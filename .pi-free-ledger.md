## Decisões (usuário)

- **D1 — Copilot fora.** Não usar `COPILOT_GITHUB_TOKEN`/Copilot em nada do pipeline (custo da conta GitHub).
- **D2 — Keys existentes entram.** Usar as keys já configuradas (OpenRouter, Cloudflare Workers AI, NVIDIA NIM, Ollama Cloud, Mistral) para ampliar alcance e rate-limit.
- **D3 — Competência na classificação.** Modelos devem ser os mais competentes PARA ESSE tipo de classificação (structured output + instruction following), não só "gratuito e vivo". Ranquear por eval em casos reais de categorização (`catalog:evals`), não só índice estático.
- **D4 — Load balancing entre réplicas.** Free tem rate limit; se o mesmo modelo bom existe em >1 provider, usar os vários para balancear (mesma qualidade = mesma tier).
- **D5 — Ledger obrigatório.** Anotar tudo: decisões, pedidos, status, plano. Este arquivo é a fonte de verdade barata e clara.

## Plano (P3) — pool dinâmico + ranking por eval + balancing

### Fase 1 — Foundation (estrutura de dados)
- **F1.1** Normalização de família: `familyOf(modelId)` → ex. `openrouter/deepseek/deepseek-v4-flash` e `cloudflare/@cf/deepseek/deepseek-v4-flash` → família `deepseek-v4-flash`. Estrutura `ModelReplica { family, replicas: [{provider, modelId, authKey?}] }`.
- **F1.2** Probe-cache com TTL (ex.: 6h) + auto-hide de modelo morto até re-probe; persistir em `.cache/pi-free/probes.json` (gitignored).
- **F1.3** Snapshot atômico do pool: `.cache/pi-free/pool.json` (famílias, réplicas vivas, score, ordem), escrita tmp+rename.

### Fase 2 — Discovery (ampliar com keys)
- **D2.1** Fetch por provider usando as keys configuradas: OpenRouter `/api/v1/models` (filtrar `:free`/pricing 0), Cloudflare Workers AI `/models`, Mistral `/v1/models`, Ollama Cloud `/api/tags`. NVIDIA NIM: sem provider no pi-ai → **decisão pendente** (ver Abertos).
- **D2.2** Pool = seed curada (`PI_FREE_MODEL_CYCLE`) ∪ descobertos free; dedup por família.

### Fase 3 — Ranking (competência na classificação)
- **R3.1** Usar `catalog:evals` com suite pequena de casos reais de categorização para scorear cada família viva (pass-rate + latência).
- **R3.2** Tiering: famílias por pass-rate; réplicas dentro da tier mantêm ordem AA-index como tiebreak.

### Fase 4 — Balancing
- **B4.1** Seleção runtime em `ai.ts`: escolher réplica viva de melhor tier; round-robin entre réplicas da mesma família (rate-limit spread).
- **B4.2** Doctor reporta status por réplica (vivo/morto/latência/tier), não só modelo.

### Fase 5 — Integração
- **I5.1** Refresh do pool em `catalog:sync` (fase antes de categorize) + paridade CI (mesmas keys no workflow).
- **I5.2** Testes focados TDD por fase (regressão observada → implementar → rerun).

## Abertos (precisam decisão)
- **A1 — NVIDIA NIM.** `NVIDIA_API_KEY` setada mas sem provider no pi-ai. Opções: (a) deixar morta; (b) upstream provider NIM no pi-ai (fora de escopo); (c) usar modelos NVIDIA só via OpenRouter (`openrouter/nvidia/...`). **Recomendado: (c)** — zero código novo, key continua útil p/ rate-limit do OpenRouter.
- **A2 — Fronteira custo.** Seleção permanece em modelos free; keys só ampliam alcance/rate-limit. Se um dia quisermos paid no ciclo → decisão explícita nova (hoje não existe caminho pago no código).
- **A3 — Budget de eval no sync.** Scorear N famílias × M casos tem custo/tempo. Proposta: top-K=10 famílias vivas, suite pequena (~8-12 casos), cache de scores com TTL; dentro do budget de 1h da categorize.
